# 工作汇报的页面文案

面向听众表达业务信息。先弄清发生了什么、影响是什么、接下来谁做什么或需要决定什么，再写页面。正文不替生成工具解释它如何核验，也不模仿口号式管理汇报。

## 页面怎么写

- 标题尽量给出这一页的具体结果、变化、问题或请求。例如“10月利润比预算少282万元”，比“深化经营分析，推动提质增效”更有信息。封面、目录及信息不足的页面不硬凑结论或数字。
- 正文用具体对象、常用动词和已有事实。能写“A区销售少了150万元”就不写“区域增长动能承压”。能写“陈敏11月5日前完成权限申请”就不写“夯实前置能力，形成交付闭环”。
- 不靠“赋能、抓手、协同、闭环、多维、全链路”等词撑气势；这些词有明确专业含义时可用，不做机械黑名单。删掉后不损失信息的套话直接删掉。
- 每条只承担一个信息点。不为了凑三栏、五步或整齐句式添加内容；不要把工作动作改写成抽象的“体系建设”。没有新增信息时不设总结卡。
- 结论有多少把握就说到哪一步。直接写“原因待核实”“验收时间待定”“建议由销售负责人牵头”，不用“在证据未充分闭合前不作确定性因果归因”包裹它。
- 不自证“没有编造、严格核实、可追溯、不是因果证明、不能保证”等。除非它本身是听众必须了解的方法或风险，否则放在作者记录，不占业务正文。

## 必要限定放在哪里

| 内容 | 放置 |
|---|---|
| 结果、变化、责任、期限、具体待决事项 | 标题／正文 |
| 原因尚未核实、责任安排尚待确认 | 对应句子或简短状态，一处说明清楚即可 |
| 会改变结论的期间、范围、分母、样本限制 | 对应结论旁的短注；不能全藏进备注 |
| 会影响决策的适用条件、成本、交付影响和替代选项 | 决策页正文；条件与后果不能删成无风险承诺 |
| 一般核验过程、全部引用、原始材料定位、完整前提及反证 | 提纲／演讲者备注；必须保留 |
| 模拟数据声明、许可署名、用户要求或业务必需的法定提示 | 保留规定位置；不因“去防御”删除 |

finding.text及claim.text要能独立表达支持范围内的含义；不能把一句过强的结论留下，再只在limits中悄悄限定。limits/validation保留全文于提纲与备注，生成器不再逐句机械拼到正文。

## 前后对照

| 原表述 | 业务写法 |
|---|---|
| 观察事实与待验证解释分开 | A区销售下滑150万元，排班影响待核实 |
| 下一步行动先明确验收标准 | 一周内复核A区线索与排班 |
| 前提未核实前不执行；反证触发必须回退 | 需先取得订单级贡献和可避免成本 |
| 以上请求均待确认，前提未核实前不承诺选项后果 | 待确认：是否安排一周跨区排查？ |
| 验收安排按用户指令明确保留待定 | 验收时间待定 |
| 记录支持的阻塞／解释边界 | 验收卡在测试权限 |
| 构建协同闭环，推动质量提升 | 由运营汇总异常订单，周五前提交处理清单（仅当资料支持该安排） |

这些是表达方式的示例，不是可直接套用的业务事实。

## 出稿前的文案检查

逐页读标题和正文，核对是否有对象、事实或具体安排；删掉空泛口号、重复免责声明和与本页无关的方法说明。检查删改后，原来的不确定性、待确认状态和关键决策风险是否仍清楚，数字与指标含义是否保持一致。结构化校验不能判断全部语气和蕴含关系，这一轮需要逐句编辑并结合真实预览核对；不要宣称脚本能量化“AI味”。
